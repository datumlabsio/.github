# Getting help

## If you work at Datum Labs

Ask in the crew channel for the repo first. Someone has usually hit it before.

If it turns out to be a real defect or a missing capability, open an issue on the repo so it does not live only in a Slack thread.

## If you are a client

Talk to your forward engineer. They are the route in, and they can raise it with the platform team on your behalf.

## Where questions go

| Question | Where |
|---|---|
| Something is broken in a repo | An issue on that repo |
| How do I build X the Datum way | [datum-standards](https://github.com/datumlabsio/datum-standards) — start at the README |
| I think a rule is wrong | An RFC against [datum-standards](https://github.com/datumlabsio/datum-standards/blob/main/CONTRIBUTING.md) |
| A security vulnerability | [SECURITY.md](SECURITY.md) — never a public issue |
| Who decides this | [GOVERNANCE.md](https://github.com/datumlabsio/datum-standards/blob/main/GOVERNANCE.md) |

## What we do not use issues for

Arguing about a rule. That is what RFCs are for, and the reason is simple: an issue thread ends with whoever got the last word, and an RFC ends with a decision and reasons that the next person can read.
